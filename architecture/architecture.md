# Lab Architecture

## Overview

This project uses a small virtualized detection-engineering lab built around Wazuh and Sysmon.

The lab was designed to reproduce a realistic defensive monitoring workflow:

`Windows endpoint activity -> Sysmon / Windows Event Logs -> Wazuh Agent -> Wazuh Manager -> Detection Rules -> Threat Hunting Dashboard`

The objective was not only to generate alerts, but to understand how telemetry is produced, collected, parsed, matched against rules, and finally presented to an analyst.

---

## Components

### Windows 11 Endpoint

**Hostname:** `WIN11-ENDPOINT`

The Windows endpoint represents a monitored workstation.

It was used to:

- generate controlled security-relevant activity;
- run Sysmon;
- collect Windows Security events;
- collect Task Scheduler events;
- collect Microsoft Defender events;
- run the Wazuh Agent;
- validate process, registry, account, and security-control telemetry.

Examples of tested behaviors included:

- encoded PowerShell;
- hidden PowerShell execution;
- PowerShell web requests;
- Windows Script Host spawning PowerShell;
- local Administrators group modification;
- Scheduled Task creation;
- Registry Run Key modification;
- Microsoft Defender Tamper Protection;
- MSHTA execution with a remote URL;
- Certutil remote retrieval attempts.

---

### Sysmon

Sysmon provides detailed endpoint telemetry beyond standard Windows logging.

The lab primarily relied on:

- **Event ID 1** — Process creation
- **Event ID 13** — Registry value set
- **Event ID 22** — DNS query

Useful fields included:

- process image;
- command line;
- parent process;
- parent command line;
- user;
- hashes;
- target registry object;
- DNS query name.

Sysmon Event ID 1 was the most reliable source for custom live detections in this lab.

---

### Wazuh Agent

The Wazuh Agent installed on `WIN11-ENDPOINT` forwards Windows telemetry to the Wazuh Manager.

Additional event channels were configured through `ossec.conf`, including:

```xml
<localfile>
  <location>Microsoft-Windows-Sysmon/Operational</location>
  <log_format>eventchannel</log_format>
</localfile>
```

```xml
<localfile>
  <location>Microsoft-Windows-TaskScheduler/Operational</location>
  <log_format>eventchannel</log_format>
</localfile>
```

```xml
<localfile>
  <location>Microsoft-Windows-Windows Defender/Operational</location>
  <log_format>eventchannel</log_format>
</localfile>
```

These channels were added progressively as new detection scenarios were investigated.

---

### Wazuh Manager

The Wazuh Manager receives and analyzes endpoint events.

It was used to:

- decode Windows Event Channel telemetry;
- apply native Wazuh rules;
- apply custom detection rules;
- map detections to MITRE ATT&CK;
- test rules with `wazuh-logtest`;
- inspect raw archived events during troubleshooting.

Custom rules were stored in:

```text
/var/ossec/etc/rules/local_rules.xml
```

Only rules validated in the live pipeline were retained in the production ruleset.

---

### Wazuh Indexer and Dashboard

The Wazuh Indexer stores security alerts generated by the manager.

The Wazuh Dashboard was used for:

- Threat Hunting;
- alert validation;
- rule-ID filtering;
- MITRE ATT&CK visibility;
- inspection of event fields;
- investigation of process relationships and command lines.

Examples of validated custom alert IDs include:

```text
100100
100102
100104
100106
```

## Network Layout

The virtual machines communicate over the VMware NAT network.

Example addresses used during the lab:

```text
Wazuh Server   : 192.168.90.128
Windows Agent  : 192.168.90.134
```

The Windows agent communicates with the Wazuh Manager over the Wazuh agent communication ports.

The lab is isolated from production systems and is used only for controlled testing.

## Detection Flow

A typical custom detection follows this path:

```text
Controlled activity on Windows
            |
            v
      Sysmon Event
            |
            v
       Wazuh Agent
            |
            v
      Wazuh Manager
            |
            v
      Custom Rule Match
            |
            v
     MITRE ATT&CK Mapping
            |
            v
       Wazuh Indexer
            |
            v
     Threat Hunting Alert
```

For example:

```text
mshta.exe https://example.com
            |
            v
     Sysmon Event ID 1
            |
            v
     Custom Rule 100106
            |
            v
       MITRE T1218.005
            |
            v
     Threat Hunting Alert
```

## Rule Lifecycle

Rules were not automatically considered production-ready after being written.

The lab followed this maturity model:

```text
Idea
  |
  v
Telemetry validation
  |
  v
Native coverage check
  |
  v
Custom rule development
  |
  v
wazuh-logtest
  |
  v
Live validation
  |
  v
Noise / false-positive review
  |
  +----------------------+
  |                      |
  v                      v
Production           Experimental
```

Production rules were kept separate from experimental rules in the repository.

---

## Design Principles

The architecture was guided by several principles:

- validate telemetry before debugging rules;
- prefer behavioral context over executable names alone;
- check native Wazuh coverage before creating custom detections;
- use real endpoint events for final validation;
- keep experimental detections separate from production rules;
- preserve evidence of both successful and unsuccessful scenarios;
- document limitations instead of forcing unsafe or unrealistic behavior.

---

## Scope

This lab focuses on:

- defensive security;
- endpoint monitoring;
- detection engineering;
- SIEM analysis;
- MITRE ATT&CK mapping;
- alert validation;
- detection tuning;
- troubleshooting.

It does not attempt to reproduce a full enterprise SOC or production network.
